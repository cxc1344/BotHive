# OpenGrokBot v0.3 PRoot rollout and product roadmap

## v0.3 Linux runtime design

- One persistent Alpine minirootfs per Bot under `filesDir/linux-rootfs/<botId>`.
- One persistent workspace per Bot at the existing `filesDir/sandbox/<botId>` path, mounted into the guest as `/workspace`.
- The compressed Alpine minirootfs archive is cached once per device ABI; each Bot gets its own extracted tree, `/etc/apk` database, installed packages, `/root`, and temporary directory.
- PRoot and its loader are packaged as Android native-library assets (under `jniLibs`) at build time. This avoids attempting to execute a downloaded ELF directly from a writable cache directory on Android.
- First shell use (or the Settings self-check) downloads a roughly 4 MB Alpine minirootfs, validates it with the upstream SHA-256 manifest, and extracts it. Subsequent shell calls reuse the Bot's rootfs.
- At most two PRoot commands run concurrently to avoid overwhelming a phone. Each Bot's own PRoot startup is serialized.
- The guest gets `/dev`, `/proc`, and its own `/workspace`; no `/storage`, `/system`, or broad host app-data bind is intentionally added.

## Important isolation boundary

PRoot provides a Linux userspace and path/identity emulation; it does not create a new Linux kernel, PID namespace, mount namespace, network namespace, cgroup, or hardware-backed VM. The Bot's commands still run under the Android application's UID. Per-Bot rootfs directories prevent ordinary accidental file overlap, but they are not a hardened hostile-code boundary. Guard remains a heuristic, not a security boundary. Do not expose untrusted Bots to secrets or sensitive host files on the assumption that PRoot is equivalent to QEMU/Firecracker.

## Rollout validation checklist

1. Build with `bash tools/fetch_proot_android.sh` before `gradle assembleDebug`.
2. Install on a real ARM64 phone and run Settings → Self-check for a Bot; verify Alpine version, `uname -m`, and `/workspace` output.
3. Run `apk update`, `apk add python3 git`, and a small script; confirm network/DNS and executable permissions on the target device.
4. Create two Bots; create a file in Bot A and confirm it does not appear in Bot B's `/workspace` or rootfs.
5. Reset one Bot and confirm the other Bot's package database, files, and installed packages remain intact.
6. Test 30-second timeout, long-running child processes, app force-stop, and Android battery restrictions.
7. Run the full build/test workflow on all four ABIs before publishing. This patch has not been built or verified on a physical Android device.

## Product upgrades inspired by Grok Bot

The most valuable product patterns to borrow are not simply “more tools”; they are persistent work, reusable process, and user control. Official Grok Bot docs describe reusable Skills, scheduled/event-triggered Routines, long-term memory, shared persistent computer resources, computer/browser use, connected apps, and explicit approval boundaries.

### P1 — high value, relatively local to this app

- **Artifact center and controlled exchange:** list files produced in `/workspace`, preview text/images, export/share, and attach artifacts to a project. Because Bot rootfs/workspaces are separate, add an explicit project-scoped `/exchange` handoff area with clear read/write ownership instead of bind-mounting all Bot folders into every other Bot. The manager should review actual artifacts, not only narrative claims.
- **Approval inbox:** tools that send messages, delete data, publish, purchase, or change external systems produce a pending action card. User approval is separate from the manager's review.
- **Usage ledger:** record model, provider, prompt/output tokens where provided, latency, estimated cost, shell seconds, and per-Bot/project budgets. Add hard limits and a global concurrency setting.
- **Context compaction and per-Bot memory:** preserve recent turns plus a user-reviewed memory summary; keep each Bot's role memory separate from shared project facts.
- **Skills library:** store reusable `SKILL.md` procedures with trigger, inputs, steps, validation, outputs, and approval requirements. Enable selected Skills per Bot.

### P2 — bigger features

- **Routines:** schedule a saved Skill through WorkManager, with pause/resume, run history, retry policy, and notification on completion. Android background execution is best-effort and cannot promise 24/7 execution like a cloud computer.
- **MCP/connectors:** start with a small MCP client and user-granted integrations; keep every connector permission explicit and revocable.
- **Browser/computer use:** WebView/browser per user profile with screenshot and bounded actions; login and sensitive actions require user takeover/approval. A mobile app should not claim the same persistent cloud-computer behavior as Grok Bot.
- **Task DAG and artifacts:** let the manager define dependencies, validate outputs, and resume from completed nodes instead of only launching every assignment in parallel.

## Suggested implementation order

Linux runtime → workspace/artifact browser → approval inbox → usage ledger → Skills → Routines → MCP connectors → browser/computer use.
